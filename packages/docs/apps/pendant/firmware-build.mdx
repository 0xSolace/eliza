The Eliza pendant v3 firmware is a small Omi DevKit1 variant derived from the upstream [BasedHardware/omi firmware](https://github.com/BasedHardware/omi). Upstream is distributed under the [MIT License](https://github.com/BasedHardware/omi/blob/main/LICENSE), with copyright attributed to Based Hardware Contributors. Eliza retains that provenance while changing the reference identity, configuration, and release gate. The local audited firmware lane is not yet public, so a truly public local build still requires publishing that lane or an equivalent source release.

## Initialize the NCS Workspace

The build script requires a pre-existing NCS workspace and refuses to run when `nrf` or `zephyr` are not at the pinned commits. Initialize that workspace with the same immutable container used by the build gate:

```bash
mkdir -p /path/to/ncs-ws
docker run --rm \
  -v /path/to/ncs-ws:/ncs-ws \
  ghcr.io/zephyrproject-rtos/ci@sha256:3e43c81b93271ee93c23adbcb65eb1ad5621bd9ada296a2a129f560b6310e565 \
  bash -lc 'set -e; cd /ncs-ws; export CMAKE_PREFIX_PATH=/opt/toolchains; \
    west init -m https://github.com/nrfconnect/sdk-nrf --mr v2.7.0; \
    west update; \
    west zephyr-export'
```

Verify the revisions before building:

```bash
test "$(git -C /path/to/ncs-ws/nrf rev-parse HEAD)" = \
  5cb85570ca43bc344d3145c2338128eacf4b48ec
test "$(git -C /path/to/ncs-ws/zephyr rev-parse HEAD)" = \
  100befc70c74f7ec83dd8ac3171ee18eeddb4dbd
```

These commands are the validated NCS `v2.7.0` initialization path. The gate checks the two revisions above. A published firmware source should also ship its complete `west` manifest lock so builders can audit every transitive module.

## Run the Build Gate

From the unpublished firmware lane, the validated command is:

```bash
omi/firmware/devkit/scripts/build_verify_eliza_pendant_v3.sh \
  --ncs-workspace /path/to/ncs-ws \
  --output-dir /path/to/output/eliza-pendant-v3
```

The script never flashes hardware. It runs a pristine `west build`, copies UF2, BIN, and HEX outputs, then verifies the release artifact.

The underlying `west build` command is:

```bash
west build -b xiao_ble/nrf52840/sense --pristine always /omi/firmware/devkit -- \
  -DNCS_TOOLCHAIN_VERSION="NONE" \
  -DCONF_FILE="prj_eliza_pendant_v3.conf" \
  -DDTC_OVERLAY_FILE="/omi/firmware/devkit/overlay/xiao_ble_sense_devkitv2-adafruit.overlay" \
  -DCMAKE_EXPORT_COMPILE_COMMANDS="YES" \
  -DCMAKE_BUILD_TYPE="Debug" \
  -DPLATFORM=nrf52840 \
  -DCACHED_CONF_FILE="/omi/firmware/devkit/prj_eliza_pendant_v3.conf"
```

## Invariants

The release gate and host invariant test reject:

- mutable Docker image tags;
- NCS `nrf` or Zephyr revisions that differ from the pinned commits;
- malformed UF2 block magic;
- a UF2 hash that differs from the verified v3 hash;
- missing `eliza` or `eliza pendant` identity strings;
- legacy `Friend`, `Friend DevKit`, `Omi DevKit`, or `Omi DevKit 2` identity strings;
- FLASH or RAM overflow;
- loss of the Omi audio service, data characteristic, codec characteristic, codec ID `20`, or standard Battery Service;
- re-enabling immediate UART logging or console output;
- re-enabling DK2-only `OFFLINE_STORAGE`, `SPEAKER`, or `HAPTIC` on the DK1 target.

Run the static invariant test in the firmware lane:

```bash
python3 omi/firmware/devkit/scripts/test_eliza_pendant_v3_invariants.py
```

## Why DK2 Features Stay Off on DK1

The v3 config differs from the renamed v2 config by disabling exactly three features:

```text
CONFIG_OMI_ENABLE_OFFLINE_STORAGE=n
CONFIG_OMI_ENABLE_SPEAKER=n
CONFIG_OMI_ENABLE_HAPTIC=n
```

Those features can hard-return before BLE starts on a bare DK1:

- `mount_sd_card()` returns before `transport_start()` when no SD card is present.
- `speaker_init()` can fail before transport on hardware without the DK2 speaker path.
- `init_haptic_pin()` can fail before transport on hardware without the haptic motor path.

The app only needs microphone to BLE audio. Keeping those DK2-only paths disabled makes BLE startup the first feature-critical boundary.

## Publication Prerequisite

The source branch and release gate described here currently live in a separate unpublished firmware lane. Public documentation can describe the verified digest and process, but public builders cannot reproduce it until the firmware source, release script, and source commit are published. A public release should include the UF2, BIN, HEX, `SHA256SUMS`, build manifest, source commit, and the exact NCS workspace lock or revision instructions.
